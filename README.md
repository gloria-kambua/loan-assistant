# Microfinance Loan-Application Assistant

A prototype for checking microfinance loan applications against written lending rules. It will
extract application details, report which rules pass or need review, and cite the policy behind
each failed rule. A person—not the model—will make every approval or rejection decision.

> **Status:** Prototype setup, November 2026. There is no runnable application yet. Development is
> planned with fictional applications and public sample policies only.

## The problem

Reviewing applications by hand takes time, and policy checks or rejection reasons can be applied
inconsistently or left undocumented. I want to test whether a small, explainable assistant can
make those checks easier to review without taking the decision away from a loan officer.

## Scope and phases

- **v0.1: individual loans.** Start with one borrower and a flat set of fields to learn structured
  extraction before adding group complexity.
- **v0.2: rules, tool calling, group loans, and PDF input.** Add a nested list of members and
   group-level checks after individual-loan extraction is working.
- **v0.3: policy retrieval.** Retrieve relevant policy sections with RAG and cite them in the
   review results.
- **v0.4: evaluation.** Measure extraction and rule-check performance against labeled test cases.
- **v1.0: deployment.** Deploy the application on AWS and make a demo available.
- Include a `loan_type` field from the start so the data model can distinguish `individual` and
   `group` loans.
- **Text input first.** PDF input is planned for v0.2; OCR can come later.
- **Amazon Bedrock from the start.** Use its Converse API so the model can be changed through
   configuration rather than tying the application to a single model vendor.
- The assistant returns extracted fields and a `pass` or `needs_review` result. It never
   recommends approval or rejection.

Bedrock development should use a personal AWS account, not an employer’s account or credentials.
Set a low billing alarm and enable access to the chosen model before running the prototype. Actual
cost depends on the selected model and usage.

## Intended workflow

1. Provide an individual loan application as text.
2. Extract structured fields such as loan type, requested amount, purpose, income, and guarantor
   details.
3. Check those fields against deterministic Python lending rules.
4. Retrieve relevant sections from policy documents with RAG and attach citations to failed rules.
5. Give a reviewer the results to verify and decide.

## Definition of done for v1.0

- At least **90% field-level accuracy** across at least **10 labeled loan applications**.
- At least **3 deterministic lending rules** covered by tests.
- **100% of rule failures** include a citation to the relevant policy source.
- A deployed demo demonstrates the flow using fictional applications and sample policies.

## Planned v0.2 group-loan rules

- Add group applications with a list of members.
- Validate group size, member loan caps, group meeting history, and member defaults.
- Extend the labeled test set and evaluation to cover group-member extraction and group rules.

## Human review

Credit decisions affect people’s livelihoods, and an LLM can be confidently wrong about an
application or policy. The assistant can organize evidence, but a qualified person must verify it
and own the final decision and its consequences.

## Out of scope for v0.1

- Group-loan extraction and group-specific rules (planned for v0.2), production applications, or
  real borrower data
- Automated approval, rejection, or credit scoring
- PDF input (planned for v0.2), OCR, and loan servicing
- AWS deployment (planned for v1.0) and production integrations

policy. In this example, the applicant’s debt-to-income ratio exceeds the stated maximum.

```json
{
  "status": "needs_review",
  "loan_type": "individual",
  "applicant": "Jane Doe",
  "requested_amount": 250000,
  "currency": "KES",
  "rule_failures": [
    {
      "rule": "Maximum debt-to-income ratio",
      "observed": 0.42,
      "maximum_allowed": 0.4,
      "reason": "The observed debt-to-income ratio exceeds the policy maximum.",
      "citation": "Sample Policy, Section 4.2"
    }
  ],
  "human_decision": null
}
```
